# Askly v1 → v2 검증 계획

## 현재 판단

- 질문 생성: 기존 6개는 쉽고 Judge도 입력 문맥만 보고 높은 점수를 주는 경향이 있어
  실제 취약점을 구분하기 어려웠다.
- 답변 평가: 기존 결과에서 `specificity`와 `logical_structure` 오차가 상대적으로
  컸다. 전체 Spearman도 항목 108개를 펼쳐 계산해 해석이 부정확했다.
- Router: 18개 Case에 69/70점, 질문 9/10/11개, 꼬리질문 1/2개 등의 경계값이
  포함되고 Accuracy 1.0이므로 추가 v2는 만들지 않는다.

## 최소 수정

| 대상 | 현재 문제 | 원인 | 최소 수정 |
|---|---|---|---|
| 질문 생성 | 일반적인 질문도 개인화 만점 | Judge가 질문보다 입력 문맥의 풍부함을 과대평가 | 질문 문장에 드러난 근거만 평가하도록 Judge 앵커 명시 |
| 질문 생성 | MATCH/PARTIAL에서도 지원자 근거가 질문에 약하게 드러남 | 프롬프트가 깊게 묻도록만 지시 | 확인된 프로젝트·기술·역할 중 하나를 질문에 명시 |
| 질문 생성 | 여러 `missing_points`를 한 질문에 묶을 위험 | 우선순위와 단일 항목 규칙이 약함 | 가장 우선적인 한 항목만 묻도록 명시 |
| 질문 생성 | JD에만 있는 기술을 사용했다고 전제할 위험 | UNVERIFIED 중립 질문 규칙이 추상적 | 기술 사용을 전제하지 않고 경험 유무·유사 경험 질문 |
| 답변 평가 | `specificity`가 결과 수치 유무에 영향받음 | 구체성과 결과 명확성의 경계가 겹침 | 구체 정보가 있으면 수치가 없어도 별도 평가 |
| 답변 평가 | `logical_structure`에 세부 정보 부족이 중복 반영됨 | 항목 독립성 지시 부족 | STAR 형식을 강제하지 않고 흐름만 평가 |
| 답변 평가 | 전체 Spearman 해석이 모호함 | 6개 항목을 펼친 순위 상관 | Case별 종합 점수 순위 상관으로 변경 |

## 실험 절차

1. v2 dev에서 v1 baseline 실행
2. 실패 Case와 항목별 오차 확인
3. 위 최소 수정만 적용한 v2를 같은 dev에서 실행
4. 핵심 지표가 개선되고 치명적 회귀가 없는지 확인
5. 프롬프트를 더 수정하지 않고 holdout v1/v2를 각각 한 번 실행
6. `evals.compare_experiments` 결과표와 대표 실패 Case 2~3개를 포트폴리오에 기록

결과가 개선되지 않으면 수치를 숨기지 않고 원인과 다음 가설을 기록한다. Dataset이나
Human Label은 v2 결과를 본 뒤 유리하게 바꾸지 않는다.
